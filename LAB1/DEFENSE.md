\# DEFENSE - Завдання 1: Домен і модель даних (ER)



\*\*Намір і критерії:\*\*

Побудувати концептуальну ER-модель для інтернет-магазину книг. Головні критерії: узгодженість типів, коректне найменування сутностей  та виділення асоціативної сутності `OrderItem` для фіксації історичної ціни.



\*\*Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:\*\*

1\. \*Розбіжність:\* У згенерованій моделі для замовлення (Order) був відсутній атрибут загальної суми чека.

&#x20;  \*Виправлення:\* Додано атрибут `total\_amount` до `spec.md`, модель перегенерована. (Коміт: `update spec to add total\_amount to Order`)

2\. \*Розбіжність:\* ШІ самостійно обрав тип `float` для грошових полів, що є помилкою для фінансових БД.

&#x20;  \*Виправлення:\* Зафіксовано вимогу в `spec.md` щодо використання типу `DECIMAL`. (Коміт: `enforce DECIMAL type for money values in spec`)

3\. \*Розбіжність:\* ШІ згенерував назви сутностей у верхньому регістрі (напр., `ORDER\_ITEM`), що порушує конвенцію найменування.

&#x20;  \*Виправлення:\* Додано критерій щодо використання `PascalCase` для всіх сутностей. (Коміт: `enforce PascalCase for entity names in spec`)



\*\*Ключове рішення - які альтернативи зважив і чому обрав цю (ADR):\*\*

\*Рішення щодо ціни товару:\* Можна було брати ціну книги безпосередньо з таблиці `Book`. Але обрано варіант дублювання ціни в асоціативну сутність `OrderItem` (`price\_at\_purchase`). Це гарантує, що при зміні ціни книги в каталозі, сума старих замовлень не зміниться.



\*\*Перевірка - узгодженість із попередньою моделлю (як перевірив):\*\*

Перевірив згенерований ШІ рендер Mermaid проти `spec.md`. Переконався, що всі атрибути, типи та регістр на діаграмі збігаються з текстом специфікації. Усі виправлення робилися виключно через оновлення `spec.md`.
